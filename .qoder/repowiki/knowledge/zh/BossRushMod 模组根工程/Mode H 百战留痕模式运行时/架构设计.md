## 2026-08-29 第二次事故：调用点存在但转换表不放行

上一节接通了编排层，随后一批（看盘 / 赔率 / 锁盘 / 分帧生成校验）却踩了**同构但更隐蔽**的坑：这次调用方都在，调用却必然失败。四个 P0 全部是「运行时调用 vs 冻结表 / 关停闩锁」的断裂，编译与当时 33 条 guard 依然全绿。

**根因与修复**：

- **锁盘按钮永远无效**：新代码按错记的表写成 `LoadoutEditing -> LoadoutLocked`，而冻结表里锁盘只有 `OddsPreview -> LoadoutLocked` 一条边，且全仓没有任何调用转入 `OddsPreview`。玩家点锁盘只会得到一行 DevLog，而赔率页是 `ClaimModalInput` 的时停模态页、没有关闭按钮，只能靠游戏自身 ESC 菜单逃生。修复：主干改为 `MatchBrief -> LoadoutEditing -> OddsPreview -> LoadoutLocked -> MatchSpawning`，开页即推进到 `OddsPreview`（同一个页面既是配装也是看赔率），锁盘前再幂等补一跳兜底。**不改冻结表**。
- **回滚退看盘的转换非法**：`MatchSpawning` 在冻结表里没有直达 `MatchBrief` 的边。改为经 `Recovering` 过渡，由下面的恢复驱动落回同一场；这一支**刻意**用不消耗重试预算的 `RequestRecovering`——功能没写完不是技术故障，消耗预算会把赛季推进死路。
- **`Recovering` 是死态**：所有技术故障出口都转进 `Recovering`，却没有任何调用点以它为源转出去，`MaxAutomaticTechnicalRetriesPerMatch=2` 的预算永远走不到第二次。新增 `DriveRecovery`（在 `OnUpdateInternal` 里按 stateSequence 判重驱动，每次进入只尝试一次）+ `ResolveRecoveryResumeLifecycle`（战前战中一律回落**同一场** MatchBrief，早期与幕间状态回落自己）+ `RequestTechnicalRetry`（消耗预算 → 未超预算走 Recovering，超预算挂起）。**恢复驱动必须异步（下一帧）**：`EnsureMatchPlan` 是在页面组装里报故障的，同步回落会变成无限递归；同理，页面组装路径上的故障必须消耗重试预算，否则「回落 → 重建页面 → 再失败」会变成每帧一次的死循环。
- **关停闩锁永不复位**：`_commandsClosed` / `_shutdownCompleted` 只在 `OnAwake`（每进程一次）复位，一次会话只能玩一局；再次入场时船票已预扣、模块却对所有命令静默早返，玩家站在无人接管的原图上。新增 `BeginNewRunSession()`，在**意图匹配成功之后**复位闩锁与每局一次性字段（顺带清掉残留的 `_pendingContractMainId`）——放在意图匹配之后，才不会因为「路过一张受支持地图」就解除关停状态。

**同批补齐的可玩性缺口**：`AbortSetup` 现在给玩家一句归类文案 + 退票告知（新增 7 个 `Abort_*` key，由 `ResolveAbortMessageKey` 把内部 reasonId 归类）；入口被拒有 `ShowUnavailableNotice`；`GetReasonLocalizationKey` 改为白名单式 fail-safe，未注入的内部原因（如 `entry_exception:NullReference`）回落通用文案，不再可能显示 `*星号原文*`；船坞入口接通**恢复分支**（有待处理赛季记录时打开恢复壳而不是拒绝玩家，但有其它模式在跑时不接管）；换档/删档回调补 `ModeHRuntimeModule.NotifySlotRestored()` 重建内存 run owner——此前存档恢复只在 `OnAwake` 跑一次，从主菜单载入中断赛季时 recovery-only 闸立不起来，玩家可以直接开新赛季**静默覆盖**它；`RouteUiForLifecycle` 离开恢复通道时收起恢复壳；`EnsureMatchPlan` 缓存判据补上 `technicalRetrySequence`（只比 matchIndex 会让技术重试复用刚失败的同一份计划）；看盘页 `Label_Match` 改用 `Replace("{0}", …)`（此前直接拼接，页面显示「第 {0} 场 1 / 6」）；`ResetModeHStaticCaches` 补 `ModeHSaveFlushCoordinator.ShutdownSubscription()` 退订（4.6）。

**`ModeHReachabilityGuard` 增补两条断言**：① 两端都写死的 `TryTransition` 调用点，其 (from, to) 必须在冻结表内；② 恢复通道三态（Recovering / ErrorRecoveryPending / Suspended）一旦被进入，就必须有以它为源的转换调用点。只查恢复通道是因为普通玩法状态可由 `RequestRecovering` 这类**动态源**门面退出，静态归属不了、硬查会误报；而恢复通道是所有故障路径的终点，出口只能写死源状态——正好是出事的那条不变式。两条都做过反例验证（注入即红、还原即绿）。教训升级为一句话：**上一次是「构件在、没人调」，这一次是「有人调、调不通」；guard 断言「有调用方」还不够，必须断言「调用会成功」。**
