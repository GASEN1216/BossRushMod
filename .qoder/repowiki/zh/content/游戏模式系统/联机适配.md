# 原版 COOP 房间适配

状态：2026-10-18 独立目录复审，开发分支 `codex/coop-full-compat`；证据分 L1 接线、L2 隔离验证、L3 实机房间。当前实现不能代替 L3 多端验收。

目标是 [Escape From Duckov COOP Mod](https://steamcommunity.com/sharedfiles/filedetails/?id=3591341282) 原版 API，作者为 Mr.sans & InitLoader。接口核对使用[作者源码](https://github.com/Mr-sans-and-InitLoader-s-team/Escape-From-Duckov-Coop-Mod-Preview)的 `65d13a96f47697eac863178f0c3542779299d618`，并对照本机安装 DLL。房间人数沿用上游能力（上游提供 2–16 人设置），适配逻辑遍历实际成员，不固定两人。未安装该联机模组时走原单机逻辑。

## 所有权和接线

世界状态由房主产生：模式入口、波次、Boss、共享机关、宝箱库存与世界 NPC。每个玩家自己提交装备、关系、商店付款、个人成长、任务和永久奖励。客户端镜像不得重复生成有伤害能力的 Boss 控制器或重新填一份共享战利品。

## 原生地图投票与真实扣票

本机安装的 COOP 在地图项点击时接管官方 `MapSelectionView.LoadTask`，原生投票完成后直接发起加载，整个替代路径没有调用官方 `Cost.Pay`。因此仅因入口来自地图界面就标记“已预付”会放行免费进入，E/F/G 还可能登记没有付款的退款。2026-10-18 复审将此记录为 `CR-2026-10-18-015`；实机验收尚未闭环，不能据此声明候选版可发布。

[地图付款兼容 owner](file://Common/Coop/BossRushCoopMapPaymentCompatibility.cs) 只接管本模组自定义地图的房主付款，沿用原生投票和加载协议。在第一次 BeginLoad 广播前，冻结并复核实际地图项、同一 `Cost.items`、原角色及物品根、官方场景实例、房间、资产、槽位和入口意图，调用一次官方 `Cost.Pay`；只有真实付款成功并再次通过归属核对，才允许原生广播及后续房主加载。付款前取消不扣费，客人、单机和其它地图不走这次补扣；相同投票重入不能再次支付。自有单票地图的客人点击在真实 Entry / Notify 两个原生入口前提示由房主发起，客人仍可打开原生地图界面参与准备。丧尸专属地图项禁用了原生 Entry，沿自身的客人请求、房主裁决协议处理，不套用这次补扣或禁用该请求。消费结果不明时阻断重复操作，不把异常当作“未扣费”自动补票。

[付款回执](file://MapSelection/BossRushCoopMapPaymentReceipt.cs) 将真实付款交给原有模式入口；已发布的付款由原模式负责，未发布的确定付款才交回原资产的唯一退款 owner。换角色、换槽或换房后，旧义务不能迁到当前玩家。已消费的原场景真正退役后，下一次地图选择可以建立新的付款上下文，不能因为旧回执常驻而阻断第二次进入。Windows 编译、回归及三端真实扣票/取消/重复出入结果分别记录在修复台账中。

原生 COOP 接管地图点击后可能绕过官方 WaitForConfirm，原有初始出生选择不会建立 pending。普通 BossRush 与 Mode D 因此在 `SetupCoopClientEntry` 的真实场景绑定完成后，使用与房主相同的 `GetDefaultPositionForScene` 世界坐标，仅对当前本机身体补一次对齐，再建立本地路牌和救援点。已到达的初始出生不重复 `SetPosition`；位置回调若换房、代次、资产、身体或场景，后续设施不再初始化。E/F/G/H 沿各自落点入口处理。重复的世界快照仍经 token + handle 调度去重，不能持续传送玩家。该修复已有 L1 / L2，三端真实位置与战斗仍须新候选 L3。

## 协议与恢复

网络 DTO 和内嵌的物品 / 亡魂 / 模式 JSON 使用 `BossRushCoopJson`，解析复用共享 JSON token。真实游戏发现动态 Mod 类型即使标注 Serializable，Unity JsonUtility 也可能省略自定义元素数组；原离线 System.Text.Json 替身无法暴露这个问题。新映射保留数组、List、官方 CustomData 私有 SerializeField 与完整 UInt64 种子，不读取远端类型名。缓存由联机 RuntimeModule 销毁时清理。测试须使用同一生产 codec，并另保留真实游戏传输证据。

房主给原生 NetPeer 分配房间身份，重连凭证只能恢复本房间的离线成员。来自客人的身份字段不决定 owner；客户端也不能用接收侧 `IsServer` 推断发送者。命令校验房间、场景代次和递增序号；世界快照只有房主可发布，并拒绝过期版本。

2026-10-13 独立复审补齐 Direct 断线事件缺失的原生连接表对账，快速重连先退休旧 peer 再恢复参与者；hello 与 welcome 使用请求序号，阻止旧槽身份和旧房间回执倒灌。切房时重置旧 roster 序号、场景代次与成员。`CoopSession` 链接完整生产运行时执行这些分支，原生网络和 Unity 仍为替身。

同轮真实三端在全员死亡后，房主名单 alive=0，两客端却各自将两个健康远端代理判断为活人。原生代理的 Health.IsDead 不能成为客端远端存活权威；roster 增加房主真实 alive，绑定当前资产、场景代次和实际角色引用。本机及房主继续读官方 Health.IsDead，未知、缺席、断开、换体和新 Scene 实例清掉旧事实，同图重载尚未收到新代次时不恢复旧图名单。CoopSession 逐字抽出完整生产 player，验证 16 人名单发送与实际消费，旧实现转红、新实现通过；游戏修后名单仍需再次 L3 采样。

2026-10-15 续审发现连续同名旅行仍不能只凭 sceneId 或本地 handle 变化绑定房主 generation：旧第 31 次消息可误占实际第 32 次 Core，随后正确第 32 次消息反而要求再重载。`BossRushCoopSceneIdentity` 在真实原生 Begin 发送前附带本 Mod 的旅行 token，在原生 RPC 入站且进入 Mod 消息队列前观察，再用官方开始加载事件与实际新 Core 绑定。原生 RPC 参数和执行保持原样；没有唯一旅行标识的 curtainGuid 不作为代次身份。

客端先登记待绑定 generation，实际 Core/token 匹配前不向玩法暴露新代次。首次稳定同图加入允许采用初始 token；观察到真实旅行后禁止退回此捷径。绑定包只确立场景，下一份完整 roster 才恢复远端生命事实。客端先到的新 Core 准备 key 保留到对应代次，旧 Core 的 key 不继承。原生加载先于客端 runtime 更新或 welcome 时，仅保留随后接受的精确新房间记录；切房、断线结束和销毁清理旧状态。完整 Runtime、SceneIdentity 与 player 的联合离线回归覆盖这些交错，安装版原生 IL/Harmony 另核边界；修改后的三端 L3 待复验。

准备屏障同时绑定资产 incarnation 与房主分配的连接 epoch。A→B→A 递增资产 revision，切槽或新连接清退旧准备；完整 ready 成员快照带单调 revision，逐成员核对资产和 epoch，不能用累加旧成员处理撤回。相同 Core 重连可在新 welcome 后重新声明准备；旧连接在途 welcome 和 ready 不得恢复旧状态。

联机 DLL 与 Assets 指纹一致后才允许玩法命令。世界快照周期补发以支持迟到者，个人交付用稳定收据 ID 重试并等待成功确认。房主自己的交付失败也进入队列；跨场景不丢未确认收据。离线收件人不阻塞当前房间成员返程。传输队列是房间运行期内存，不能据此保证主机进程中止后的所有未提交奖励恢复。

同房重连的空 RunId 窗口保留收据去重和待交义务；收到不同的非空 RunId 才切换房间账本。控制租约的授予、心跳与释放带 revision，释放墓碑挡住迟到授权，新租约挡住旧释放，避免镜头与操作对象被乱序消息重新劫回。

玩法命令同时绑定实际场景 token 与成员准备 epoch，发送失败保留请求，乱序命令等待连续序号。房主在进入业务回调前消费该序号，并在回调退出时确认分发；业务回调即使在部分副作用后抛异常，也不会因同一请求重发而再次执行。这个确认只证明已经分发，付款、退款与奖励是否成功仍由各业务的账本和个人收据确认。E/F/G/H/Zombie 的周期事实重报使用 `RequestRepeat`：同一原事务仅复用当前房间、成员、Core、资产、准备 epoch 和 token 完全相同的未确认请求，确认后仍可重新上报。手动请求和不同事务各自保留，不能靠数量上限或超时删除有效交互。

亡魂、宠物、NPC、配偶、召唤及世界效果在实际消费与异步续作处复核当前 Core/token；只在接收消息时检查代次不足以防止同图重载后的同编号实体被旧缓存重新绑定。个人经验、死亡事实及永久交付继续使用原拥有者收据，不因世界尚未绑定而清账。亡魂在新房握手前登记的墓箱请求保留原 Core 与资产，只允许该 Core 认领随后到达的房间身份，每条有效记录仍独立生成。

鸭王征程的个人资格在实际模式入口冻结，使用原模式 epoch、房间、旅行 token、资产和已接受合同版本。第一次 Campaign 世界快照迟到不能遗漏真实入场资格；收据到达不能重新武装当前新局或新合同。换图后已经获得的原局事实继续投给原合同，死亡房主仍按存续的世界模式发布给当时活着的玩家。世界击杀计数与个人连续收据取同一事实的最大下界，避免重复相加。

同一 Core 内切换 A→B→A 时，原局进度对象、无伤失败状态、精确累计秒数与完成通知状态一起恢复，离开 A 的时间不计入 A。各份个人撤离租约与世界事实租约共享这批进度和计时对象。Mode F 个人入口早于 Campaign 每帧观察时，也先核对真实新 epoch，避免把上一局进度装进新局撤离账本。取消或重新接受合同使旧版本失效；原资格不存在时不借晚到事实创建资格。上述边界由完整生产追踪器、联机模块、投递与 codec 的离线执行证明，实际三端任务流程仍要单独验收。

共享变异的客端词条缓存绑定房间、场景代次与 token，新的实际 Core 不沿用旧词条。死亡爆炸协程在暂停与恢复后都验证该归属；击杀治疗沿原规则属于当前场景即时效果，等待当前场景绑定后执行，旧场景治疗确认取消。各玩家原数值、效果数量和房主世界爆炸规则保留。延迟击杀效果还冻结原玩家资产和 ReadyEpoch；同一身体切档及 A→B→A 都会取消旧即时续作。治疗明确发给原资产，交付回调后再复核归属才执行世界爆炸，避免存档回调切槽后继续作用于新玩家。永久收据仍按原资产补交，不受这个即时效果取消规则影响。

原生 AI 编号允许负数，只有 0 无效。场景加载投票返回的 CompletedTask 仅表示请求已提交，模块必须检查真实场景、关卡初始化与角色到达；旧波次和旧场景请求不能作用于新状态。世界机关使用房主共享 key 映射原生可破坏物 ID，不能用两端不同的层级 sibling index。

世界箱完整清单由真实 codec 编码后分片，不以截断箱数满足消息上限。接收方按房主、场景代次和快照版本收齐再替换，丢片期间继续保留已有世界；重复、旧版本和其他来源不覆盖新状态。发布与实际应用都要求绑定当前 Core，未绑定的完整快照不得修改或删除本地箱子。同坐标箱逐个分配独立原生映射，冲突搜索按实际箱数处理。

原生 Loot 管线负责唯一库存；适配层只补客户端的可交互外壳。装备 RF_/AFX_ 字段经类型清单、清零/移除与基线恢复后应用，避免重发叠加数值。远程特效只投影表现，伤害由房主或原生玩家伤害通道完成。

原版 COOP 会在客端预测 AI 死亡后追加 99999 点强制击杀上报；当客端没有房主完整护甲属性时，这会提前杀死仍有生命的亡魂或 Boss。`CoopAiPredictionHealthProtection` 只保护显式登记的 Mod AI，限制在本机攻击上下文内，真实房主死亡快照仍可写入。`CoopAiPrediction` 夹具使用实装 Harmony 验证原伤害保留、强制上报抑制、嵌套与异常恢复。

实际开始旅行到新 Core 绑定期间，数字 generation 暂不前移，不能用它单独认可旧世界包。特效、危险体和 AI 预测授权另外携带非空旅行 token，生产发布与消费都要求 `HasBoundScene`；同 ID 新角色只接受当前精确 token。保护 marker 冻结房间、代次和 token，真实 Hurt 准入及 lethal setter 都复核；Begin 到 owner 下一帧清理之间也立即失去旧保护。清理永久镜像角色与撤销临时预测资格分别处理，房主加载前合法待登记实体在新 Core 绑定后仍可发布。54 项生产方法/Harmony 执行断言以及稀疏副本反向证明是 L2，不能代替新一轮游戏实测。

同一 marker 另行保留实体出生时的复制体角色或房主房间。停止 COOP 后全局门面的单机判据会恢复，但旧复制体不能因此获得世界伤害资格，旧房主实体也不能重绑另一房间。世界实体入口用 `HasEntityAuthority` 检查原实体；预测 owner 清理只解除生命保护，不擦除实体出生归属。新单机实体、新房间新实体正常取得资格，存量局内状态由各模式或旅程的原 owner 清理。

## 丧尸模式的波次与个人效果（2026-10-18）

丧尸业务命令在共享通道的原房间、Core/token、资产及准备 epoch 之外，再携带本局 Run 与当前 Wave。起始流派及拒绝入场仅约束本局，其他世界效果和准备完成命令同时约束当前波，防止同图内旧请求落到后续玩法。奖励视图冻结当次抽卡 token，重抽、换资产、离开奖励阶段后旧按钮不消费新选项。

新局先清上一局参与资产表，再依原 starter 确认重新准入。客端安全圈随真实中心与半径替换；撤离坐标使用房主现态，机会提示按波显示，反复快照不重新夺取输入，开始倒计时关闭，取消后允许重新提示。

击杀相关奖励由房主真实死亡事实确认原生攻击者，按原参与资产及已选择层数结算。额外净化星只由房主生成；客人回血走 `CoopPersonalDelivery` 的 `ZombieKills` 收据，执行处复核局、波、场景 token 与资产。连杀爆炸由房主登记 run-only 下一帧任务，保留客人来源、原数值及效果伤害防递归；房主死亡不取消仍存活客人的合法爆炸。存档/永久奖励交付仍沿原账本，瞬时战斗效果不能延期到新波或新局。

Boss 目标与找点使用已准入原资产的存活队员。刷怪最近候选先排序，找到可达点即停；同帧失败复用结果，所有合资格导航锚点无效才早退，Boss 找点失败退避一秒。初始化使用尚未领取起始物的实际活人，Active 仍要求个人准入。弹药补给按手持口径、缺失时回退开局口径；重弹药保底与属性封顶沿主线修复接入。

召唤法杖和霜之哀伤的本机异步召唤同样冻结 `CoopBossCreationLease`，进房、换房、断线后不激活旧任务生成物。实装 API、守卫、隔离运行与反向验证见根 `CODE_REVIEW_FINDINGS.md`、`FIX_TRACKER.md` 本日记录；真实伤害、导航和多端时序仍要 L3。

## 截信人的持久托管与原物领取（2026-10-18）

本轮 `COMPAT / SCHEMA+ / WIRE+` 沿 `CoopWaylayerJournal` 的原槽位 store 与保存协调器扩展；schema1 缺失 Grants/claim 字段按空值读取，老 protocol0 unknown 与 protocol2 已公开或结果不明的保守核账含义不变。新 protocol3 在房主账本托管一件完整原树，Success 还未确认时实物保持私有，强杀后若实际磁盘已是 Success，可恢复可交互的锁定领取凭证，不能以只剩责任树视为已交付。世界凭证进入首领包、原生 ItemSnapshot 构建、死亡尸体箱及地面掉落时保留锁，不能直接作为可保存/合堆的真实原件交给玩家。

真实拾取或 AddAt/Plug 尝试向房主请求领取。房主从实际 transport 绑定当前角色、资产与持久 journal GUID，拒绝两个 peer 对同一 GUID 的歧义绑定；每笔仅持久冻结一个 claimant。领取者离线时账本保留义务，原身份以新的进程资产租约唯一握手后，`CoopPersonalDelivery` 恢复同一收据；原房主换槽时不能用新槽接管旧槽责任。位置取原生 ActiveAgent、实际首领或尸体箱锚点，不用子物品的初始 transform。副本或旧房/场景 nonce 不取得新原件。

个人领取先持久 Grant，随后只有精确原件→实际本人包→一次 AddAt 的权限。同步通知不能借此 Detach、Drop、Plug、Combine 或再次 Add 到其它位置；新增消费门同时覆盖实际 Use 与 CA_UseItem 完成扣量，未标记/解锁物品继续原路径。写盘失败保留同一实例，不重新 factory；独立原件在原身体死亡后可按严格租约经原生 RemoveItem 迁入本人新活体，混合退款堆不自动整堆搬走。首领/尸体票据的原生构建与普通尸体 O(1) 早返由独立 NativeBuildScope 接线。

owner 本次明文批准 PC06 领取、追回与明确 Failure 退款增加一次官方角色物品保存。`PublishOriginal` 写实际 `Item/MainCharacterItemData` 与同批 Returned proof，复用共享每帧保存门，ES3.File 完整读回当前原生树并再次核同一 owner/slot/path/asset/活体/根/原件归属后，才能 NoteReturned、解锁与 ACK。它会提前落盘当前整份角色物品树，范围仅此原件发布，不保存 Health、仓库或 CollectSaveData，也不扩成后续所有物品转交的事务系统。自然保存重载同样依实际 GrantKey/Returned proof 去重；退款原堆+1 的通知中只有真实 mutation 后才附带返还证明。

当前证据为生产接线、Windows 真实游戏程序集引用编译、生产链接执行及新 PID 强杀/文件恢复的 L2；物理存储/库存 seam 不等于 Unity ES3 或真实 COOP 传输。三端 slot3 连续原盘的真实故障、host 重启、原件可用和整树保存/重载仍待 L3。已发布 PC06 原物与完全无其 metadata 的普通实物，均须做实际 Drop/Pickup→另一端保存→强杀来源→同盘重启对照，分别核实际拥有树与 journal 重造；不能用离线旧树回滚推断实机已复制，也不能把 factory=0 单独当成原物可用通过。
