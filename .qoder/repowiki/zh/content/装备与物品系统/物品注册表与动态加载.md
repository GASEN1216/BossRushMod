# 物品注册表与动态加载

## 2026-11-20 冷启动读回武器与仓库物品

角色和仓库都会经过官方 `ItemTreeData.InstantiateAsync`。官方先按 TypeID 创建实例，再写入该实例的存档变量，最后按保存的槽键和库存格位组装整棵树。仓库可以收下官方生成的问号空壳。装备槽会检查标签，拒绝空壳后，下一次角色保存可能丢掉这条槽位关系。因此必须在实例交给官方装配之前取得配置完整的 prefab。

首次只请求装备包也要先登记物品和装备配置器。工厂分别记录配置完成和正式发布成功，按目标 TypeID 检查官方动态表。定向注册可接管后台刚取消的同一个原生资源请求。克隆物品由集成运行时持有，表项失效时可补发，自建 prefab 被销毁时可以重建。正式版会按 TypeID 记录最终注册失败。

官方同步入口在常规条目缺失时可能访问空引用。如果动态表仍引用已销毁的 Unity 对象，官方实例化也可能抛出异常。已登记的 BossRush 类型在这些情况下可走官方 fallback 入口。外层异步创建若首次登记失败，只对尚未交付的同编号官方空壳或空结果等待一帧重试。正常读档沿用原时序，角色装备的选择仍由游戏决定。缺失资源持续不可用时看日志里的物品编号和启用目录。已经被旧存档覆盖的武器节点和配件信息无法从剩下的空槽推断。

新增或调整注册计划时，同一 TypeID 重复声明会令冷读档回归报出编号。正式版保留首条计划，后续物品仍可登记。Guards 工作流中的「角色装备与仓库冷读档」在独立 Windows 环境执行这些回归。可用 `tests/AGENTS.md` 中的物品恢复命令在本地复跑。

如果物品编号齐全，但注册路径误指另一个合法资源包，回归会比对该包实际导出的物品编号与模型名。此清单由 [包内物品清单生成器](file://tools/item_bundle_inventory.py) 从资源包生成。发布资源检查会重新打开待交付的实际文件，校验根 prefab 和 SHA-256。

## 2026-09-25 船票与配置表归属

`BossRushDynamicItemRegistry.cs` 的船票同步注册和蛋糕、日志补注册入口，以及 `ItemContentRegistry.cs` 的配置器登记表，现归同一 `IntegrationRuntimeModule`。原宿主入口在 `BossRushIntegration.cs` 保留薄转发。动态初始化闩和运行时确认的船票 TypeID 仍为进程静态状态，由模块持有；初始化内部直接读取该状态并调用配置器表。

船票仍先检查已登记 prefab，再按 bundle 原枚举顺序加载物品，逐件追加 `Key` / `SpecialKey` 并登记；目标 TypeID 优先，未见目标时保留首个正 TypeID fallback，最后在 `finally` 卸载 bundle。配置器表与装备回调顺序未改，登记失败仍沿原防崩路径继续其余初始化。

## 运行时克隆兜底

收集品、遗种蛋、潮闸镇、天空岛和新武器等共用 `RuntimeItemFallback`，各配置器仍决定克隆来源的顺序和属性。直接调用物品入口时先按注册计划检查 bundle。兜底回调查询官方 prefab 时绕过按需补丁，同一 TypeID 的回调重入不会再次克隆。

官方注册拒绝时销毁这次新建的克隆，下次查找重试。已成功注册的克隆还活着但官方条目丢失时，可以补登同一实例。已销毁的克隆会重建。集成运行时卸载时，只注销和销毁它持有的克隆，已接替同 TypeID 的 bundle prefab 仍可保留。

来源：[克隆兜底](file://Integration/Items/RuntimeItemFallback.cs)、[集成运行时](file://Integration/BossRushIntegrationRuntimeModule.cs)、[潮闸镇回归](file://tests/fixtures/TidegateTreasure/Program.cs)。

## 简介
本文件系统性阐述 BossRushMod 的物品注册表与动态加载系统，重点围绕 BossRushDynamicItemRegistry 的架构设计、物品注册机制、动态加载流程、内存管理策略；并详解多种游戏内物品的实现（消耗品、关键物品、模式专属物品）；说明物品配置系统 ItemConfig 的工作原理（含 JSON 配置解析、运行时修改、数据验证）；解释物品使用系统 Usage 的实现（触发逻辑、效果应用、状态管理）；最后提供新物品开发的完整指南以及性能优化与错误处理策略。

## 核心组件
- 动态注册中心：BossRushDynamicItemRegistry
  - 职责：维护 TypeID 到“注册计划”的映射；在首次需要时按需加载 Bundle、执行特殊/回退加载；保证 prefab 可用；记录失败日志且仅一次；支持批量与全量注册。
  - 关键能力：
    - EnsureRegistered(typeId)：单例按需注册
    - EnsureAllRegistered()：全量注册
    - HasRegisteredPrefabWithoutEnsuring(typeId)：检查是否已就绪
    - ResetStaticCaches()：重置内部缓存
- 内容配置器注册：ItemContentRegistry
  - 职责：集中注册所有物品的 ConfigureItem 回调，供 ItemFactory 在加载对应 TypeID 时调用。
- 物品配置类（Config）：每个物品一个静态类，负责设置显示名、堆叠数、价值、品质、标签、绑定 UsageUtilities 与 UsageBehavior。
- 使用行为（Usage）：继承 UsageBehavior，实现 CanBeUsed 与 OnUse，封装触发条件与效果。

## 详细组件分析

### 动态注册中心：BossRushDynamicItemRegistry
- 设计要点
  - 注册计划（RegistrationPlan）：声明某 TypeID 所需的装备/物品 Bundle、特殊加载器、回退加载器。
  - 构建阶段（BuildPlans）：集中声明所有受管 TypeID 及其加载策略。
  - 运行阶段（EnsureRegistered）：
    - 若已存在预制体则直接返回
    - 若正在加载中则短路避免重复
    - 依次尝试：特殊加载器 → 装备Bundle → 物品Bundle → 回退加载器
    - 最终校验是否成功，否则记录一次警告日志
  - 安全与健壮性：
    - 通过 IsPatchBypassed 控制递归防护
    - 统一异常捕获与 DevLog
    - InProgress/FailureLogged 集合避免重复工作/重复告警
- 内存管理
  - 仅在首次访问时加载 Bundle
  - 对 AssetBundle 进行显式卸载（例如 bossrush_ticket 的特殊加载路径）
  - 通过 ItemAssetsCollection.AddDynamicEntry 将动态条目加入全局索引

### 物品配置系统（ItemConfig）工作原理
- 注册机制
  - 每个物品定义 TYPE_ID、BUNDLE_NAME、本地化键、描述等常量
  - 通过 ItemFactory.RegisterConfigurator(TYPE_ID, ConfigureItem) 注册配置器
  - ItemContentRegistry 集中调用各 Config.RegisterConfigurator() 完成统一注册
- 运行时修改
  - ConfigureItem 中可动态设置 DisplayNameRaw、MaxStackCount、Value、Quality、Tags 等
  - 通过反射为 UsageUtilities 注入 master/useTime，并将 UsageBehavior 加入 behaviors 列表
- 数据验证
  - 大量 try/catch 包裹反射与外部调用，失败时记录 DevLog
  - 对空引用、缺失组件、字段不存在等情况做防御性处理

## 2026-11-26 读档没装上的 Mod 装备：装备抢救（COMPAT）

玩家反馈「每次重进 Mod 都加载不出来，身上的 Mod 武器装备也消失了」。官方 `ItemTreeData.InstantiateAsync`（`ItemStatsSystem.dll`，用 ikdasm 核对过 IL）遇到查不到 prefab 的 TypeID 时，造一个保留 TypeID 的 `FallbackItem_<id>` 空壳；往父物品挂槽时丢弃 `Slot.Plug` 的返回值，插不进去只打一句 `Found Unplugged Item while Loading Item Tree!`。装备槽要检查标签，空壳插不进去，就成了不在任何物品树里的孤儿。官方下次 `SaveMainCharacter`（撤离、死亡、切场景前）只写挂在角色身上的东西，这件装备连同配件和背包内容就丢了。

两种情况会走到这条路：本 Mod 激活得比读档晚（创意工坊 Mod 要等 Steam 查询回调才激活，网络慢时玩家已经点了「继续」；激活时只要已身处关卡场景就算迟到——官方 `LevelManager.CreateMainCharacterAsync` 先 await 恢复角色物品树、再 await 生成角色、最后才写 `mainCharacter`，用 ikdasm 核对过 IL，本 Mod 在这几帧里激活时读档失败没有补丁记号，主角也还是空的）；或者本 Mod 在场，但读档时某件装备一时注册不上（`DynamicItemRegistrationPatchSupport.NeedsFallback` 为真，这时会调 `BossRushEquipmentRescue.NoteUnresolvedLoad()` 记一笔）。

[BossRushEquipmentRescue.cs](file://Integration/BossRushEquipmentRescue.cs) 的处理方式：
- 只看主角，只在上述两种情况各跑一次：关卡初始化完成后再让一帧，读出存档里还没被覆盖的 `Item/MainCharacterItemData`（要求 `LevelConfig.SaveCharacter`，记录根 TypeID 与活角色一致）。
- 按槽位键逐层对照记录与活角色：记录里是 Mod 物品、活角色那个槽为空，才算候选；槽里换了别的东西说明玩家本局动过，不碰。
- 证据门槛：场景里必须找得到同 TypeID 的空壳孤儿（名字是官方 `FallbackItem_<TypeID>`，不在任何父物品、背包或槽里）。孤儿只可能来自读档失败，没有证据的候选一律跳过，避免把玩家本局卸下、卖掉的装备再变出一份。
- 证据扫描只看已加载场景里的对象（含未激活，`FindObjectsByType` 不排序），不连同物品预制体资源一起过一遍。
- 用官方 `ItemTreeData.InstantiateAsync` 从记录重建整棵子树（耐久、配件、背包内容都在记录里）。重建要等几帧：等完先核对存档槽（`SavesSystem.CurrentSlot`）、关卡实例、主角、角色物品都没变且原父物品还在，变了就销毁重建品、整轮作废、旧孤儿不动，不把旧档装备送给新档角色；核对通过才销毁旧孤儿。真物品先插回原槽（空槽、`CanPlug`、插完核对 `slot.Content`），插不回进背包；仍是空壳或放不回身上的进仓库（仓库满时官方转进快递缓冲，同样整棵序列化），记录随存档保住，下次资源就绪读档即恢复。
- 本类型从不直接写存档。玩家提示中英双语；正式构建输出一行 `[BossRush] 装备抢救 reason=... candidates= restored= preserved= skipped=`。

挡不住的情况：读档时本 Mod 根本没在运行、玩家随后撤离或切场景，官方已经把没有这件装备的角色写回存档。这时只能在主菜单的「Mod 变更」提示里点取消，或用官方的存档备份恢复。守卫 `tests/EquipmentRescueEvidenceGuard.py`（18 个变异探针）；`DynamicItemInitialization` 夹具证明「注册成功不记、持续缺失记一笔」；`EquipmentRescueTiming` 夹具执行生产抢救与迟到判定，覆盖生成主角期间激活、主菜单激活不做任何事、重建期间换槽换关卡、只换槽、什么都没变五种情况。在真实游戏里的效果仍要 L3。
