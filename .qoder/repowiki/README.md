# BossRushMod 仓库知识库

这里保存面向开发者和 AI 协作者的详细代码知识。开始实现功能前先读仓库根目录的 [`AGENTS.md`](../../AGENTS.md)。本知识库用来快速定位资料，**不能替代当前代码、构建脚本和 guard 对事实的确认**。

## 现状（2026-09-14 盘点）

- 知识库的底子是 2026-08-12 用工具生成、08-13 导入的快照（319 个文件，约 4.7 MB），其中大部分文件之后没有再改过。
- **持续维护**的是后来手写或手工扩写的专题：天空岛、Mode H、丧尸模式、局内随机事件、遗种巢、鸭皇图鉴、鸭王征程、竞技场后山、日报、词缀锻造、自定义武器与套装、捏脸 NPC、UI 系统集成。这些文档通常在代码改动后几天内更新，里面有代码注释里没有的设计理由。
- **按快照对待**的部分（可能已过时，引用前先核对代码）：
  - `knowledge/zh/BossRushMod 模组根工程/` 下几十张几百字节的「概述 / 技术栈 / 特殊配置与命令」小卡；
  - `zh/content/项目概览/` 与其下 `核心功能特性/` 这棵和主题目录重复的树；
  - 配置管理、本地化系统、标准 BossRush 波次、根工程架构这几篇（代码之后又改了很多次）；
  - 所有 `#Lx-Ly` 行号锚点——一半左右指向之后改过的文件，只能当「大概在哪」的提示。
- 冲突时的优先级：**当前代码与脚本 > `AGENTS.md` 与子系统 `AGENTS.md` > 本知识库 > 历史设计稿**。

不知道文件名时，直接搜两个正文目录：

```powershell
rg -n "关键词" .qoder/repowiki/knowledge/zh .qoder/repowiki/zh/content
```

**搜到的单条要看它在哪个小节里。** 很多文档按日期记录每一批交付，小节里的「不新增 TypeID」「不加存档字段」「不重打包」只描述**那一批**的范围，后面的批次可能恰恰加了 TypeID 或重打了包。它们不是长期禁令；长期规则只以 `AGENTS.md` 和 guard 为准。

## 与其他文档的边界

- `AGENTS.md`（根与子系统）：协作规则和不可破坏契约的唯一事实来源。
- `docs/contracts.md`：外部契约、TypeID 台账、官方 API 陷阱。
- `docs/`：本地设计、教程、审查与历史资料，默认 local-only。
- `WikiContent/`：游戏内百科实际内容；`wiki-site/`：面向玩家的在线 Wiki 站点。
- `.qoder/repowiki/`：面向实现和维护的详细知识库（本目录）。

## 什么时候更新

- 改动改变了**已经有专门文档的专题**的行为、流程、配置或内容时，在同一次变更里更新对应文档。
- 新增子系统或大功能时，写一篇主题文档（放 `zh/content/` 合适的目录）；登记进 `_index.yaml` 更好，但不强制。
- 快照期的旧文档发现错误时，直接改正或在文首标注「已过时，以代码为准」，不要求一次性补齐。
- 记录某一批交付时放在带日期的小节里，范围描述写明批次；不要把一批的范围写成通用规则，也不要把 `AGENTS.md` 已有的规则再抄一份。
- 保留精确的源码路径、类型名、配置 key、TypeID、存档 key 和发布门控；不写未经确认的运行时结论。
- 删除或改名代码文件时同步引用：`tests/RepowikiReferenceGuard.py` 会检查 `file://` 链接指向的文件是否存在（不检查行号，也不检查正文是否过时）。

`zh/meta/repowiki-metadata.json` 是生成器状态，不作为理解代码的入口。用生成工具刷新知识库时一并更新；普通手工勘误不要改写其中的编码状态。
